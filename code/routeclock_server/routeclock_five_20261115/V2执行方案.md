# RouteClock 平台复盘与下一阶段执行方案

本方案以五模型平台为执行根目录。论文要检验在共享感知时间下，哪种位置预测与误差估计能够识别可复用窄束的窗口，调度器能否把这些窗口转化为更多成功传输的比特。核心实验分别改变预测器、误差管和调度器。跨层一起更换得到的是完整系统结果。

## 运行顺序与交接接口

### 1　复现输入与服务器首测

在五模型根目录运行以下命令。本地新增的审计脚本、模型选项和搜索记录均保留旧预测器默认行为。正式分片目录与旧实验分开。

```bash
python tools/v2_route_input_audit.py --checkpoint "$CHRONOS_DIR"
python tools/v2_route_input_audit.py --formal-start 0 --formal-stop 400 --device cuda --checkpoint "$CHRONOS_DIR" --out runs/v2_formal_inputs
python tools/v2_behavior_probe.py
python tools/v2_network_snapshot.py
python tools/v2_search_replay.py runs/five_pilot/results/loop_0_RC_joint runs/v2_review/search_0.csv
```

正式分片用左闭右开区间，可按任务号拆分。每路线交付输入计数和逐方法、逐时长指标两份 CSV。汇总先按航线再按行为/观测协议，报告 ADE、终点误差、角误差、有限值比例。早先六条航线用于查错；后续模型选择使用验证集。首日计量按 SERVER_RUNBOOK.md 执行，记录冷启动、热调用 P50/P95、峰值显存、每场更新数、实际批量和完整任务墙钟。720 步与 7,200 行都是待测输入；43 点周期网格保持原设置到测速结束。

### 2　冻结 16 机论文主实验

单机训练/验证/校准/测试按 1200/400/400/400 条划分。每次拟合记录命名空间、参数、种子和参考几何哈希；从单机到网络都检查几何哈希，单机同航线多个起点仅计一个统计单位。网络正式测试使用原 30 个 network/test 任务，16 机、5% 感知时间、预热与服务各 180 秒，默认随机种子 7。各方法使用相同外生轨迹、噪声场、感知成本和调度器，服务中的观测时间由各策略决定。

先补 five_campaign 的 tube 维度。训练阶段从同一批独立校准航线分别得到 Chronos 的原生管倍率和路线混合管倍率，记录它们与预测中心版本的绑定关系。沿用 tools/chronos_tube_pilot.py 和 routeclock/route_quantile.py 的实现。主表固定价值调度器，以 2 个中心 × 2 种管 × 30 场构成 120 条记录，其中 60 条 LightGBM 记录来自原 main，新增 60 条。保留固定通信、纯 IMM、纯路线和带路线 Chronos 行。固定混合权重从训练/验证冻结，若沿用 89/11 则标成先导冻结对照。动作矩阵对同一中心、同一管分别做固定两项、只调束宽、只调间隔、两项联调，后者复用主表。

主终点为配对网络净吞吐量差。并列报告窄束机秒、占比、实际持续秒/段、获准时长、感知次数与占时、受服务最差 10% 的吞吐量、行动不可用时间。全部段与窄束段分别报告失效分子和分母；一段中任一真值时刻相对同束宽理想对准的损失超过 3 dB 即计一次。按网络重采样 2,000 次报 95% 区间；失效率差区间落入原先预设的 ±2 个百分点，才使用“相近失效率”措辞。比特账本按数据占时和传输期间平均速率拆分。16 机的完整搜索采样取相同若干场景保留完整帧，复用 v2_search_replay.py 验证已选动作可重建，并报告剪枝前后候选数、能换束宽的飞机数、试换数、预算修复与最终接受数。

**已运行的 16 机单决策诊断。** 使用独立的 network/v2_diagnostic 世界、现有先导门控和管，16 机在 180 秒预热中错峰每秒观测一次，共用同一个时刻的预测。538 个几何可行动作经联调剪枝保留 89 个，16 架都还有多个可选宽度。坐标搜索测试 98 次变宽，接受 0 次；最终 15 架使用最窄束，预计感知负载 4.908%。固定 2 秒只调宽时为 7 架最窄、负载 2.480%。固定最窄束只调间隔时为 16 架最窄，但预计负载 5.167%，超过 5%。该数字是各机观测成本除以间隔的总和。budget 修复循环在无进一步降载动作时退出，仍返回当前选择，实际 token bucket 随后可能推迟观测。单个快照还没有吞吐账本。

**正式开跑前补齐预算不可行的口径。** 为每次决策记录最小可达预计负载、实际选中负载、是否存在预算可行组合、各机请求与实际服务时间、超期和失联时间。将结果区分为动作集本身无解和搜索未找到可行解两类；若允许让某架机等待，作为明确动作计服务损失，对所有策略一致。沿用现有允许排队的语义时，超过名义预计负载的帧报为预计超订，物理占时由令牌和账本另报。用本次快照复现 5.167% 与 4.908% 作回归样本，再跑 30 场，不可将固定宽度的预计超订解释为已满足所有飞机的期限。该项优先于学习调度。

### 3　分类进入系统的判定

在正式训练任务生成 30/60/120 秒前缀；所有分支在相同观察截止时刻使用同一输入。按航线分组拟合六分类随机森林，比较多数类、按训练先验抽样和当前森林；额外单报稳定路径/无可复用结构这一粗粒度任务的每类召回，阐明偏离归位如何归组。主指标为宏 F1、平衡准确率、每类召回、混淆矩阵和航线级区间。用训练集折外类别概率作为门控候选新特征，另设同容量无类别、真实类别上界。仅当验证集上类别概率既能分辨类别，又能降低角度预测损失或提升期限收益，才进入闭环。硬分支仅在同一验证划分比较误分损失。自然比例与均衡样本分表。

### 4　离线学习调度与 16 机闭环

先修基线命名。当前 edf 分支返回每机最高即时速率动作，实际观测顺序由外层 due 决定；uniform 分支在共享预算下尝试统一方阵边长。正式基线至少区分“逐机速率贪心＋按到期服务”“统一束宽”“现有价值搜索”。如新增真正 EDF，明确请求就绪、截止时刻、冲突选择与预算不可行时的规则。空可行动作要计入失联占时；核对 choose_actions 内部的预计负载与 TokenBucket 实际感知扣时，两者承担不同约束。

新增训练命名空间 network/scheduler_train、scheduler_val，建议先 40/10 场开发，再按学习曲线扩至 120/30；network/test 的 30 场只作冻结比较。每份决策样本保存任务/时刻/无人机、预测版本、误差管、观测年龄、当前动作、候选束宽与间隔、风险界、容量与令牌状态、行为策略、被选动作以及实际交付比特。监督标签和在线特征分别存储。既有事件只提供执行动作的回报，且 compact 作业只存摘要；不能从一次观测轨迹读出未执行动作的长期回报。

首版用 LightGBM 拟合动作相对现有调度器的回报差。在独立训练场景中抽取决策时刻，克隆整网状态，在同一外生世界中改变一架飞机的一项可行动作，其余候选和后续 10 秒的基准策略一致；分别推进各分支的观测、地图、令牌、通信与时间账本。标签用两分支 10 秒内全网成功比特差除以实际时长；若尾段不足 10 秒则排除。初始每个时刻抽基准动作和至多 3 个不同束宽/间隔候选，记录抽样概率与候选覆盖；训练成本按创建的分支数单列。保留满足几何界的所有候选进入离线比较，短视帕累托剪枝可能移除长期有利动作，须比较剪枝前后机会。在线以学得分数替代即时收益项，保留共享预算可行性检查，估值必须与实际执行的选择规则一致。固定世界与中心/管后比较基准价值搜索和学习打分，验证环境选训练轮次、时间窗与阈值，最终逐网络配对。单步静态反事实只有即时收益，只称即时回归；10 秒分支回报可称有限视窗策略改进。暂缓联合 PPO；Whittle 需先给出松弛问题及可指数性依据，否则命名为启发式优先级。

### 5　时序强基线与完整通信基线

优先增加从头训练的 PatchTST 风格预测器，其次为冻结的 TimesFM 2.5。平台需同时改离线样本导出、训练/加载、在线 Tracker.issue、中心注册、头拟合和矩阵汇总。原始正式 pickle 主要存预测快照和特征，不保证含监督 Transformer 所需的完整输入窗口；应导出因果观测序列、缺测掩码、发布时刻和路线协变量。统一接口返回相同预测网格的 3 维中心和可选分位数，并在服务期按实际观测重新调用。训练型模型只用训练集拟合；对照相同调参预算、长历史输入和观测通道，处理路线协变量时做独立的有/无路线对照。冻结基础模型如需额外协变量回归，应标注该回归的训练数据与计算量。只有同中心的管在校准集上冻结后才接入调度器。

这两项支撑“预测器对照”。要主张全系统优于已有波束跟踪方法，还须选一项可复现、观测假设相容的通信原生基线，将其预测、探测代价、波束码本、重选规则映射到同一信道与时钟；列出论文假设、复现差异和额外观测。预测层不能提供联合通信系统的业界排名。Mamba、PPO、Whittle、JEPA 暂列扩展。参考 [PatchTST 原文](https://arxiv.org/abs/2211.14730) 与 [TimesFM 官方实现](https://github.com/google-research/timesfm)。
